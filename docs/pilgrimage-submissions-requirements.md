# 圣地巡礼公开投稿需求草案

日期：2026-09-22。依据：本次用户要求、分享会话及当前三个工程代码。本文用于明确需求，尚未实施功能或修改云端配置。下述第一版取舍、配额和保留时长属于建议默认值，不代表已经得到逐项确认。

## 1. 目标与边界

建立「公开端提供线索 → 独立待审核区 → 管理员整理审核 → 创建或合并正式地点」闭环。

- 投稿只有两种业务类型：`new_spot` 新地点、`update_spot` 已有地点补充/纠错。仅补充照片归入后者，不增加第三种类型。
- 匿名投稿，不依赖注册登录；昵称、联系邮箱可选，邮箱和内部审核备注不公开。
- 未审核文本和图片不得进入公开地点 API、搜索、图库、分享卡片或 SSR 数据。
- 投稿独立存入 D1 投稿表和专用私有 R2 bucket；不开放现有管理员上传 API 给匿名用户。
- 审核结束前的用户原稿、照片元信息、管理员整理草案、审核决定与处理任务均存新的投稿相关表；不借正式地点 draft、img_info.uploading 或非公开图集存待审核数据。采纳决定确认后才进入正式合并流程，同库新表属于业务隔离，具体 DDL 见[实施方案第 15 节](./pilgrimage-submissions-implementation-plan.md#15-必要表结构设计ddl-草案)。
- 管理员可以部分采纳、编辑后采纳，也可以拒绝；通过审核不是原样覆盖正式数据。
- 审核结束清除投稿临时图片；已采纳图片的正式副本保留。

第一版不做账号、评论、点赞、积分、贡献排行、公开投稿列表、自动发布、自动翻译、自动邮件通知、用户提交后编辑/撤回、管理员与投稿者站内往返沟通。来源图片不由服务器自动抓取。

## 3. 公开端体验与字段

### 3.1 入口与表单

- 巡礼页面常驻「提供新地点」入口。
- 已有地点详情提供「补充 / 纠正信息」入口：点击时由详情组件将当前地点的 `spot.id` 作为 `targetSpotId` 传给投稿组件，创建投稿时一并提交，服务端校验目标后保存为目标引用。用户只看到「正在补充：地点名称」，无需查找、填写或理解 ID。这不是通过地图 URL 自动识别地点，也不会直接修改正式地点。
- 两个入口共用独立投稿表单组件，建议第一版采用适应桌面和移动端的弹层/全屏抽屉，无需新增公开路由。
- 纠错表单明确选择补充项目，仅填写拟修改内容，不要求重新填完整地点。第一版公开端以地图分享链接为主要位置输入，不展示经纬度输入框，也不要求用户地图选点；图片处理按需加载。
- 支持 zh/ja 界面；投稿正文允许只使用一种语言。进入正式数据时统一映射至当前 zh/jp 数据键。
- 提交前预览文本和照片；显示每张图片的转换、上传、失败、重试状态。失败时保留当页文本和已完成图片，不重复创建投稿。
- 最终成功才显示「已提交，等待审核」，返回投稿编号。建议提供同设备凭证查询最小审核状态；不公开原始材料和内部备注。凭证丢失不做账号找回。

### 3.2 内容字段

| 字段 | 新地点 | 补充/纠错 |
| --- | --- | --- |
| 目标地点 | 无，由管理员可改为合并已有地点 | 必填，入口自动绑定，服务端验证可投稿目标 |
| 投稿语言 | 必填，默认当前界面语言 | 同左 |
| 地点名称/线索标题 | 必填 | 可选，仅在建议修改时填写 |
| 与 milet 的关联及说明 | 必填，例如 MV 名称、片段时间或公开活动线索 | 必填，说明问题或照片内容 |
| 地图分享链接、地址/位置说明 | 优先粘贴地图分享链接；没有链接时允许具体地址/位置说明兜底，不要求经纬度 | 位置纠正时提供新地图链接或位置说明；其他纠错无需提供 |
| 来源 URL、出处说明 | 至少提供一种依据；本人实地信息可使用文字说明 | 同左 |
| 建议名称、作品名、描述、地址、标签 | 按需填写 | 按选定修改项目填写 |
| 图片 | 可选，最多 5 张逻辑照片 | 可选，可仅补充照片 |
| 昵称、联系邮箱 | 可选，邮箱私密 | 同左 |
| 权利与投稿说明确认 | 必填；有发布用途图片时确认拥有展示授权 | 同左 |

不向匿名用户开放正式状态、排序、图集 ID、R2 key、审核人、正式地点 ID 生成、路线或合集管理、marker skin 等管理字段。缺失城市/地区由管理员归类或通过现有地区管理补建。

建议文本限制：名称 200 字符、地址 500、正文及来源说明各 5000、单个 URL 2048、整个 JSON 请求 64 KiB。服务端与前端保持一致，非法数字、非有限坐标、未知字段和不合法目标直接拒绝。

### 地图链接在管理端整理

- 公开表单提示「在地图应用中打开地点 → 分享 → 复制链接」，允许粘贴分享文本并提取其中的 URL；保留必要的原始说明。地图定位链接与证明 milet 关联的来源链接分开。
- 投稿阶段只做格式、长度和协议校验，不以能否解析出坐标作为提交条件，不根据链接覆盖绑定的纠错目标。
- 审核界面提供「解析地图链接」，复用现有 `/admin/pilgrimage/map-links/parse` 及 `parsePilgrimageMapLink`，将结果填入管理员的候选字段，确认前不写正式地点。
- 现有解析器只在 URL 文本中匹配坐标，不请求网络、不展开短链接。第一版保证保存和展示分享短链；不能解析时提示管理员打开原链接核对，再粘贴展开后的地点链接或手动补坐标，不能承诺所有分享链接都自动解析成功。
- 候选坐标要区分地图视图中心与实际地点，识别提供商的坐标顺序、坐标系及展示/导航坐标，管理员核实后采纳。现有通用正则仅作基础，不把所有匹配结果当作精确地点。
- 第一版不必新增短链接联网展开服务。如后续需要，限定管理员主动触发及受支持地图域名，并逐跳验证重定向、限制超时/跳数/响应大小，禁止抓取任意投稿 URL。

### 3.3 图片用途必须区分

- 「拟公开照片」：管理员可选择加入正式地点图集；记录授权确认、拍摄者/署名偏好和说明。
- 「仅供核实的参考图」：例如作品片段截图、地图截图，只用于审核，不自动发布，审核完成后清理。
- 第一版默认不公开投稿者身份；明确选择署名时才显示审核后的署名。最小署名可进入图片说明并保留结构化来源记录，不扩展为贡献者系统。

## 4. 上传链路与 R2 隔离

### 4.1 用户流程

1. 用户填写表单并本地处理照片；未开始上传时不占用服务端草稿和 R2 空间。
2. 通过 Turnstile，服务端校验并扣减配额，创建限时草稿，返回随机 ID 与独立随机会话凭证。
3. 凭证授权申请图片上传槽位。Worker 生成 imageId 和对象 key，预占张数/字节数，再返回短期签名 PUT。
4. 浏览器将 WebP Blob 直接 PUT 至专用 R2，不通过 Pages/Worker 中转图片，不上传手机原图。
5. 调用 complete，由服务端检查实际对象、大小、类型、结构、宽高和归属，将合格内容冻结为服务器控制的审核副本。
6. 文本及图片全部就绪后最终 submit，原子地从 draft 转 pending；缺失图片必须重试或主动移除才能提交。
7. pending 后禁止用户修改文本、申请上传或更换审核图片。

所有业务 API 走公开端现有代理；唯一外部直传是服务端签发的 R2 PUT。R2 S3 凭证与来源保护密钥仅存服务端。

### 4.2 图片处理默认值（可配置）

| 项目 | 建议第一版值 |
| --- | --- |
| 可选原始格式 | JPEG / PNG / WebP；HEIC 不保证支持，无法解码时明确提示转换 |
| 原文件限制 | 单张 20 MiB；解码前尽可能读取并限制尺寸，总像素上限 40 MP |
| 高清展示图 | 长边不超过 2560，quality 初始 0.82，单张不超过 5 MiB |
| 缩略图 | 长边不超过 640，quality 初始 0.75，单张不超过 512 KiB |
| 单投稿 | 最多 5 张逻辑照片、主图和缩略图合计不超过 28 MiB |
| 转码并发 | 默认串行，及时释放 bitmap / Object URL；支持超时和取消 |
| 草稿凭证期限 | 30 分钟，到期需重新验证；未提交数据定期清理 |
| 单次 PUT 签名期限 | 5 分钟；续签复用有效槽位，不突破累计尝试限额 |

明确采用现有管理端图片上传的异步组织方式：独立浏览器 Web Worker 接收任务 ID 与 File，使用 `createImageBitmap → OffscreenCanvas → convertToBlob(image/webp)` 完成缩放转码，以消息返回 Blob；主线程协调 Promise、界面状态及后续 R2 上传。这里是用户设备上的 Web Worker，不是 Cloudflare Worker。

参考 `data-admin/src/workers/webp.worker.ts`、`src/lib/webp.ts` 与 `src/api/uploader.ts` 的实现方式，在公开端建立独立上传组件/composable，使用投稿专用 API。主图和缩略图尽量共享同次解码；队列默认串行，不能仅因 onmessage 是 async 就认为已有并发限制。组件显示等待、转换中、待上传、上传中、校验中、完成/失败等阶段，转换时用户仍可填写文本；阶段进度不能伪装为精确字节百分比。

公开端适配要求：只在客户端按需创建 Worker，避免 SSR 顶层实例化；所有格式含 WebP 都重新编码；补充 Worker error/messageerror、任务超时、移除/取消与迟到消息处理、bitmap.close 和对象 URL 清理。检测不支持 OffscreenCanvas 等能力时，允许主线程 Canvas 串行异步回退并提示处理中，回退不承诺完全无卡顿；仍无法生成 WebP 时提示更换图片，不上传原图绕过规则。

WebP 输入也重新绘制和编码，不能沿用管理员工具的直接透传；转换结果必须实际为 WebP。测试手机照片方向、透明图、超大图和低内存设备。第一版拒绝动画输入或明确提示只采纳静态画面，避免静默改变用户预期。

服务端检查 R2 实测大小、Content-Type、RIFF/WebP 块结构、真实宽高/像素数、EXIF/XMP 和动画标记；拒绝非预期元数据、越界尺寸、畸形块及不支持的编码结构。仅检查 RIFF/WEBP 十二字节不够。结构校验不等同完整解码安全保证；客户端转码是体验优化，不能充当安全边界。

### 4.3 必须解决重复 PUT 与审核对象不可变

签名 URL 在过期前可以重复使用，不是一次性票据。不能以「complete 已成功」为由继续审核原上传 key。

建议投稿 bucket 中分 `incoming/` 与 `sealed/`：用户只有 incoming 的短期写权限；complete 读取同一对象版本并验证，将这次已验证的字节写入从未签发用户写权限的 sealed key，记录 hash/ETag。后续预览、审核、转正式只用 sealed 副本。验证与复制必须绑定同一份字节/版本，避免检查后再次无条件读取造成替换漏洞。

这增加少量 Worker 二进制读取和 R2 I/O，但不承担图片解码转码。配额需将两个变体和冻结副本的存储开销计入。旧 incoming 对象在签名过期后再次清理，避免删除后被旧链接重建。

普通签名 PUT 不能仅凭 Content-Type 或前端声明的 size 证明存储入口具有硬体积上限。第一版需明确接受短时超额上传的剩余风险，以短时签名、有限槽位、完成后实测、自动清理及总量熔断控制；若要求超额字节完全不能进入 R2，需改为受控流式上传网关，与纯浏览器直传的要求另作取舍。

### 4.4 私有读取

- 新 bucket 禁止 r2.dev/公开自定义域名访问，不能接入现有公开 static 路由。
- 管理员通过鉴权的预览接口读取 sealed 图，响应 no-store、nosniff；预览同样检查审核权限。
- 浏览器直传所需 CORS 限定公开端生产域名和必要开发域名、PUT 及必要请求头。CORS 不能替代权限校验。
- 正式图片写入现有 `MILET_IMG_BUCKET`，正式路径、主图/预览图和 URL 生成保持现有 ImgInfo 约定。

## 5. 管理员审核与合并

新增「巡礼投稿」独立列表页，按状态、类型、时间、目标地点检索，分页加载。列表只拉摘要；原始详情、图片、目标选项、合并表单按需加载到独立审核组件。

审核界面提供：原始材料、来源链接、私有参考图、正式地点当前值、拟采纳值、各字段选择开关、照片逐张采纳/舍弃、处理原因、最终结果预览。

三种结果：

1. **创建地点**：从新地点投稿预填正式编辑表单，管理员补齐地区、中日文标题和坐标，明确保存草稿或发布；确认后创建正式记录。
2. **合并已有地点**：纠错默认原目标，新地点若重复也可选择已有地点；只更新管理员勾选并确认的字段。缺省/空值不代表清空；确需清空必须明确选择。
3. **拒绝**：填写处理原因，不修改正式地点，排队删除所有投稿图片。

图片默认追加，不替换旧照片、不改变封面；替换/删除旧图继续用已有管理流程。参考图不可默认选入正式图集。有地点专用图集则追加，没有则创建 `series_type=spot` 的图集并关联；若现有图集被多个地点或其他内容共用，必须显式提示并选择独立图集，避免影响其他页面。`is_public=false` 是图库业务属性，不是 R2 私有访问控制。

合并前按目标版本比对；其他管理员或正常地点编辑改过数据时返回冲突并刷新差异，不静默覆盖。原目标删除、归档或换 ID 时不能盲目创建替代地点。现有地区调整会重建 ID，应同步维护未结束投稿的当前目标引用，另外保留 original_target_id 与提交时名称/相关字段快照；无法安全跟踪时提示管理员重新选择。

审批权限建议新增 `pilgrimage_submission` subject，区分查看、审核、重试；创建/合并同时要求正式地点对应 create/update 权限，服务端校验。系统内部附图仅能操作本次审核选中图片，不能借审核端点访问任意上传资源。

## 6. 状态、持久化与一致性

建议不要保留一个长期含糊的 approved 状态：

```text
draft → pending → applying → merged
                ↘ rejected
draft → expired
applying → apply_failed → applying（有权限管理员重试）
```

- 管理员打开审核不改变状态；编辑审核草案可持久化，但真正提交时才获取处理权。
- `merged` 表示已经写入正式记录，另记结果类型 created/updated、结果地点 ID 与正式发布状态。存为正式草稿不等于公开已发布。
- 用户仅看到待审核、处理中、已采纳、未采纳、已过期等安全摘要；内部异常与审核备注不泄漏。
- 应用状态与 cleanup_status/cache_refresh_status 分离；图片清理失败或缓存刷新失败不能把已合并记录变成“未合并”，也不能重复建地点。

建议数据：

| 数据 | 主要内容 |
| --- | --- |
| `pilgrimage_submissions` | 随机 ID、类型、原始/当前目标、目标快照、原始投稿、语言、昵称/邮箱、权利声明版本和时间、凭证 hash、状态、过期时间、审核人/原因、结果 ID、版本号 |
| `pilgrimage_submission_images` | 归属、用途、说明/署名、主图与缩略图 incoming/sealed key、实测大小/宽高/hash、签名过期时间、状态、是否采纳、正式图片映射、清理状态 |
| `pilgrimage_submission_reviews` | 操作者、决定、所选字段/图片、目标版本、前后快照、幂等操作 ID、时间；不保存临时签名 URL 或凭证明文 |
| 限额/应用任务记录 | 原子配额预占、操作步骤与失败原因、重试次数、下次处理时间；可依现有 ORM 拆表 |

新增 migration、ORM 类型和白名单；索引覆盖状态+提交时间、目标 ID、过期/清理状态，操作 ID 和正式图片映射有唯一约束。

审核执行顺序：锁定版本与本次决定 → 将选中 sealed 图片复制到正式目标 key 并核验 → 在同一 D1 原子提交中写入地点/语言/图集关系、审核结果和 merged → 刷新相关缓存 → 删除投稿副本。R2 与 D1 不能视作一个跨资源事务，失败使用持久化步骤、幂等 key 和补偿清理恢复。

现有 savePilgrimageSpot 是多步写入，不可直接声称调用它即可得到事务保障。应在既有 service/ORM 内抽取可用于原子提交的保存逻辑，或提供等效的受控应用机制；不另起框架、不绕过现有地区和语言校验。

未被 D1 引用的正式副本需可识别并清理；一旦正式记录提交成功不得补偿删除正在使用的图片。任务超时必须可恢复，同一投稿重复点击、网络重试和两个管理员并发只能产生一次效果。

## 7. 防滥用和输入安全

按用户补充，**请求限流等通用防护优先通过 Cloudflare 平台能力配置**，不要求在项目中自建完整限流系统。应用重点负责投稿权限、状态和资源配额的一致性。

### 7.1 Cloudflare 配置与应用职责

| 能力 | 优先实现位置 | 要求 |
| --- | --- | --- |
| IP 高频请求、路径/方法级限速 | Cloudflare WAF Rate Limiting Rules | 在面向访客的公开站点入口匹配投稿 API，覆盖草稿创建、签发上传、complete、submit 与状态查询；不误伤正常巡礼 GET |
| 恶意请求过滤 | Cloudflare WAF 的当前套餐可用规则 | 按实际流量启用和调整；不以 CORS 或隐藏入口代替权限 |
| 按业务 key 的短窗口限速 | Workers Rate Limiting binding，按需使用 | 在现有 Worker 中少量接入调用，配置阈值；用于会话/操作级防刷，不要求与 WAF 重复建设 |
| 真人验证 | Cloudflare Turnstile + Worker Siteverify | 平台配置站点，应用验证 token、hostname、action 后才签发投稿会话 |
| incoming 临时对象过期兜底 | R2 Lifecycle Rules | 按临时前缀设置；不能无差别删除 pending/sealed 图片 |
| 审核后清理与失败重试 | Cron Triggers + 现有 Worker service/ORM | 平台提供调度，应用依据投稿状态安全清理 |
| 单稿图片数量、字节预占、归属、幂等与状态锁 | 应用与 D1 | 业务不变量必须服务端校验，不能由请求频率规则代替 |

具体规则数量、可用计数维度、时间窗口及处置动作以当前 Cloudflare 套餐为准；尚未检查账号实际配置。不预设必须升级套餐。规则不足时先保护草稿创建与上传签发，再按需补 Workers binding。

Workers Rate Limiting 是按 Cloudflare location 工作的宽松、最终一致限速，不是全局精确账本；不能用它保证全站每天严格不超过某个张数或字节数。若启用严格业务预算，仍由 D1 原子预占保证。

防护规则优先落在公开域名的 Pages 代理入口，避免后端看到代理来源后把全部用户合并计数。检查其他可访问域名、预览域名和 Worker 直连入口，确保不能绕过来源保护与必要校验。R2 S3 签名 PUT 不经过本站域名 WAF，不能声称本站限流已经限制每次实际 PUT；仍依赖有限签发、冻结副本与过期清理。

JSON API 不依赖交互式挑战 HTML 作为正常错误返回。平台拦截时前端应能处理 403/429 或非 JSON 响应，保留当页表单并提示稍后重试；应用自身限流响应提供 429 与 Retry-After。

### 7.2 应用校验与建议阈值

- 创建可上传草稿前必须通过 Turnstile Siteverify，检查 success、预期 hostname 与 action，失败/缺配置时不签发上传权限。生产和公开预览环境禁止自动跳过，开发使用测试配置。
- Turnstile token 有效 300 秒且单次使用；验证后建立短时投稿会话，不拿同一个 token 校验每张图。会话过期或风险升高时重新验证。
- ID 不是权限。匿名凭证使用至少 256-bit 随机值，数据库仅存 hash，绑定本投稿和允许操作，放请求头，禁止 query string、日志、Referer 泄漏。查询凭证需要独立有效期和最小权限。
- 同 IP 的 5 次/小时、20 次/天作为原草案的防刷目标参考，实际采用 Cloudflare 可配置窗口和阈值，不强制为复现这些数字新增 D1/KV IP 计数器。创建草稿必须纳入限流，不能只保护最终 submit。上传签发/续签另设会话尝试上限（例如 20 次），删除图片不返还已消耗的签发次数。
- 分层覆盖 IP 请求频率、会话、单稿、全站日总量和待审核积压。建议全站初始 200 稿/日及 1 GiB/日的逻辑上传预算，达到配置阈值停止签发；不是实际存储费用硬上限。
- 单稿资源预占及启用的严格全站业务配额使用 D1 条件更新/原子预占。普通请求防刷交由 Cloudflare；不另做一套 KV 读改写限速器。
- 核实 Pages→Worker 的真实客户端 IP 链路：Pages 覆盖专用来源 IP 头，Worker 仅在来源保护通过后信任；不直接信任用户传来的 X-Forwarded-For。共享 NAT 的误伤可通过配置调整。
- IP 使用带服务端密钥的 HMAC 分桶并限期保留；无可信 IP 时明确失败/降级策略，不把所有正常用户永久归到 unknown。
- 蜜罐、最短填写耗时可作辅助信号；不采集鼠标轨迹，不以“点击几次”作为真人证明，也不能替代 Turnstile 和配额。
- 投稿始终作为纯文本渲染，禁止直接 v-html。URL 仅 http/https，不自动抓取远程页面或图片；后台外链使用 noopener/noreferrer。
- 明确校验方法、请求体长度、字段类型/长度、坐标范围、资源归属、图片状态。所有 SQL 参数化。保护管理端会话沿用已有鉴权和中间件。
- 提供功能总开关、停止新上传开关、清理失败/合并失败/积压告警；日志不记录邮箱正文、密钥、匿名凭证和签名 URL。

## 8. 清理与资料保留

- 草稿 30 分钟到期后不可继续写，24 小时内清理 incoming 和 sealed 孤儿对象。
- 已采纳：只在正式副本与 D1 关系确认成功后删除全部临时副本，包括未采纳照片和参考图。
- 已拒绝：立即排队清理全部图片，目标 24 小时内完成；重试可追踪。
- pending 不使用“一律 7 天删除”这类 bucket 生命周期，否则正常排队材料会丢失。建议 30 天提醒管理员，90 天仍未处理转 expired 并清理，期限可配置。
- incoming 可用生命周期作为兜底；sealed 按数据库状态清理，正在应用的材料不被清理任务抢删。
- 建议联系邮箱审核结束后 90 天清除，匿名查询凭证结束后 90 天失效；原始材料/未采纳文本建议 180 天后清理。最小审核和图片来源/授权记录长期保留，避免删除临时照片时丢失正式内容来源。
- 所有清理按批执行、可重试，删除对象只允许来自服务端登记的该投稿 key；对账发现孤儿和已过期签名重建对象。

## 10. 第一版验收

1. 新地点和纠错两种入口正常，单语言文本、纯文本纠错及仅补充照片均可提交；未提交成功不显示待审核成功。
2. 直接访问私有图片、伪造投稿 ID/凭证、跨投稿 complete/remove、pending 后写入全部失败。
3. 缺失/重复/错误 action 或 hostname 的 Turnstile token 不获得上传权限；并发申请和删除重传不能突破限额。
4. 假 WebP、超大小、畸形块、超尺寸、动画/元数据违规被拒绝；服务端不信任客户端宽高/大小。
5. 在 complete 后使用旧签名再次 PUT，不改变管理员审核和最终发布的内容；过期重建垃圾对象可清理。
6. 管理员可仅采纳地址或指定图片，未选字段、其他语言和已有图片不变；引用来源图不会自动公开。
7. 缺少正式必填信息不能创建；新地点可保存正式草稿或明确发布；重复地点可转为合并。
8. 双管理员并发、目标 ID 变化/删除、目标版本变化、R2 复制失败、D1 失败、清理失败均有明确结果，可重试且不重复建地点/图片。
9. 成功后正式图片可读、图集计数/封面正确、巡礼相关缓存及其他受影响图集缓存失效；临时图片按期删除。
10. XSS 文本、危险 URL、越权审核、请求体超限测试通过；权限不依赖前端按钮。
11. 公开端桌面/移动端 zh/ja、照片旋转/转换失败/弱网重试均检查；SSR 无浏览器全局访问及 hydration 问题。
12. 公开端运行 type-check、build:ssr、verify:ssr:local；管理端运行 type-check、build；Worker 运行相应 Vitest。管理端联调使用 Worker 目录直接 npm run dev。真实提交测试只写隔离测试资源，不向生产巡礼数据造测试投稿。
13. 在隔离环境验证 Cloudflare 规则覆盖实际公开入口、阈值生效、正常逐张上传/重试不被误拦、前端可处理平台非 JSON 拦截响应；另验证应用单稿配额，即使平台限流容许少量超出也不能越权或增加图片槽位。
14. 从地点 A 打开纠错表单时提交目标为 A；输入地点 B 的地图链接不能改变绑定目标。新地点表单不携带上次纠错目标；管理员可解析长链接，短链解析失败仍可审核补齐；公开投稿全程无需用户填写经纬度。
15. 浏览器 Web Worker 转码时可继续输入表单，多图任务不会同时无限解码；转码失败/超时/取消可恢复，WebP 输入同样处理，SSR 加载不创建 Worker。
16. 审核草案不写正式地点或图集；失去租约的旧任务不能覆盖已审核 sealed 对象；管理员可检查实际主图和缩略图，两者均属于不可变采纳内容。
17. 缓存/清理任务与正式合并结果同事务入队；SQL 守卫失败整批回滚，权限撤销/目标变更阻止陈旧任务提交。详细阻塞清单和表结构以实施方案第 14–15 节为准。

限流补充：采用 Workers Rate Limiting Binding，同一匿名访客的全部投稿接口合计按 60 秒 2 次配置，超限 HTTP 429 + Retry-After: 60。前端提示图片处理中、稍后重试，并在提交过程中有限自动重试，保留表单和进度。D1 累计额度及 Turnstile 保持启用；R2 直传不经过此限流器。当前匿名身份按可信代理转发的访客 IP 识别，共享出口可能共用额度。


## 审核并发方案确认（2026-09-26）

第一版投稿审核沿用已有投稿/审核草稿版本校验、正式地点和图集 revision 校验，以及合并任务 lease/fence 互斥。允许多人查看和编辑同一投稿，冲突时拒绝陈旧提交，重新读取核对后再操作，禁止自动覆盖或重复采纳。

审核临时占用锁仅列为后续可选升级，不属于当前实现、验收或上线前置条件；本期不增加占用表、开始审核/领取、续期、释放和接管交互。图片处理和合并任务已有的执行租约继续保留，与人工编辑占用不同。正式地点继续采用已实现的乐观锁保护。
